# 業務分析ガイド

`harness/` にある「業務設計の教科書」ベースの分析フレームワークを使って、ユーザーと一緒に
1つの業務をAS-IS→TO-BE→HTMLレポートまで通しで作り上げるためのガイド。

読む前提ファイル(このスキルが動く間、随時参照する):
- `harness/framework.md` — 方法論のリファレンス(ムダ時間分類・優先順位マトリクス・AI活用4パターン・効果予測ロジック)
- `harness/README.md` — 全体設計とJSONスキーマ
- `harness/templates/01_業務ステップ一覧.md` 〜 `07_優先順位マトリクス.md` — 記入するテンプレート本体

## なぜ「対話形式」が必要か

このテンプレート群は本来、複数人でのヒアリング・すり合わせを前提にしている(書籍のWORKING1〜7も
グループワーク)。一度に全部の質問を投げると、ユーザーは業務の細部をまだ思い出せていなかったり、
関係者に確認が必要だったりする。**1フェーズずつ質問し、回答をすぐファイルに書き込み、
次のフェーズに進む前に軽く確認を取る**ことで、実際のヒアリングに近い体験にする。

## 状態管理の原則

この作業は複数ターン・複数セッションにまたがる可能性が高い。**進捗は会話の記憶ではなく、
`harness/cases/<案件名>/` 配下のファイルそのものに持たせる。** そのため:

- 各フェーズで得た情報は、そのフェーズが終わる前に対応するMarkdownファイルへ書き込む(会話の最後に
  まとめて書こうとしない)。
- 案件フォルダに `PROGRESS.md` を作り、フェーズ1〜8の完了状況をチェックボックスで管理する。
- スキルが再度呼ばれたときは、まず `harness/cases/` に既存案件がないか確認し、あれば
  `PROGRESS.md` を読んで続きから再開する(最初から聞き直さない)。
- セッション内の作業順序はTaskCreate/TaskUpdateでも管理してよいが、それは補助であって
  真の進捗記録はファイル側に置くこと。

## 全体フロー

```
Phase 0  案件セットアップ(スコープ確認・案件フォルダ作成)
Phase 1  業務ステップ一覧          → 01_業務ステップ一覧.md
Phase 2  個別定義シート            → 02_個別定義シート.md(ステップごとに複製)
Phase 3  前後工程のすり合わせ      → 03_前後工程すり合わせ.md
Phase 4  情報の地図                → 04_情報の地図.md
Phase 5  課題の洗い出し            → 05_課題一覧.md
Phase 6  TO-BEパターン設計         → 06_TOBEパターン設計.md
Phase 7  優先順位マトリクス        → 07_優先順位マトリクス.md
Phase 8  JSON化・レポート生成      → data.json + report.html
```

各フェーズの考え方の詳細(なぜこの質問をするか、判断基準)は都度 `harness/framework.md` の
該当節を読み返すこと。以下は各フェーズで「何を聞き、どう書き込むか」の実務手順。

---

### Phase 0: 案件セットアップ

1. まだ聞いていなければユーザーに尋ねる: 業務名、範囲(開始〜終了)、登場する担当者(レーンに
   なる単位。「営業」「経理」のような部署単位でも「Aさん」のような個人単位でもよい)、分析の目的。
   一度に全部聞いてよいが、答えが曖昧な項目は仮置きにして先に進めることを許容する(後のフェーズで
   埋まっていく)。
2. `harness/cases/<業務名を元にした短い英数字またはローマ字スラッグ>/` を作成し、
   `harness/templates/*.md` の7ファイルをコピーする。
3. `01_業務ステップ一覧.md` の「対象業務のスコープ」表に聞いた内容を書き込む。
4. `PROGRESS.md` を作成し、以下のような形でフェーズ一覧を書く:
   ```markdown
   # 進捗

   - [ ] Phase 1: 業務ステップ一覧
   - [ ] Phase 2: 個別定義シート
   - [ ] Phase 3: 前後工程のすり合わせ
   - [ ] Phase 4: 情報の地図
   - [ ] Phase 5: 課題の洗い出し
   - [ ] Phase 6: TO-BEパターン設計
   - [ ] Phase 7: 優先順位マトリクス
   - [ ] Phase 8: レポート生成
   ```

### Phase 1: 業務ステップ一覧

- 「最初の担当者は誰で、何をしたら業務が始まりますか?」から時系列に沿って聞き出す。
- 担当者(レーン)の一覧を先に確定させる。
- `01_業務ステップ一覧.md` の表を埋める。ステップIDは `A1, A2, ...` のように連番で振る
  (Phase 2以降・JSONの `id` としてそのまま使う)。
- 埋めたら該当行を要約して見せ、「これで漏れなさそうですか?」と確認してから次へ進む。

### Phase 2: 個別定義シート

- Phase 1のステップを1つずつ、`harness/framework.md`「2. 個別定義シートの書き方」の順序
  (INPUT→DO→OUTPUT→トリガー→メモ)で聞く。全ステップを一問一答で聞くと冗長になりやすいので、
  「まとめて教えてください、足りない項目は個別に聞き返します」と提案してもよい。
- `02_個別定義シート.md` のブロックをステップ数分に複製し埋める。

### Phase 3: 前後工程のすり合わせ

- 隣接するステップのペアごとに、`framework.md`「3. 前後工程のすり合わせ」の3観点
  (INPUT/OUTPUT整合性、タイミング/トリガー整合性、成果物の有益性)を確認する。
- ズレが見つかったら、Phase 2のシート(02)をその場で修正してよい。修正した場合は
  `03_前後工程すり合わせ.md` の「個別定義シートへの反映」表に記録する。

### Phase 4: 情報の地図

- ステップ間でやり取りされる情報・データが「どこで生まれ、どこに保管され、どこで使われるか」を聞く。
- 特に「探すのに時間がかかる情報」「二重管理になっている情報」がないかを意識的に聞く
  (Phase 5の課題につながるため)。
- `04_情報の地図.md` を埋める。

### Phase 5: 課題の洗い出し

- Phase 1〜4で見えてきた「時間がかかる」「手戻りが起きる」「属人化している」箇所を課題として
  列挙し、`framework.md`「4. ムダ時間の分類」の4分類(探す時間/確認する時間/問い合わせる時間/
  判断待ち時間)のいずれかに必ずタグ付けする。
- 各課題について「1回あたり何分くらいか」「月に何回くらい発生するか」を聞き、月間ムダ時間を
  算出する(所要分×頻度÷60)。ユーザーが正確な数字を持っていない場合は「だいたいの体感でよい」
  と伝え、概算値であることを明記する。
- `05_課題一覧.md` を埋める。

### Phase 6: TO-BEパターン設計

- 課題ごとに、`framework.md`「6. TO-BEのAI活用パターン」のA〜Dのどれが適用できそうか一緒に検討する。
  4パターン全部を無理に埋める必要はなく、対象業務に合わないパターンは「対象外」でよいと伝える。
- 採用するパターンごとに、変更後の業務フロー(Phase 2と同じ粒度でステップを書き直す。
  `framework.md`の「後工程からの逆算」に倣い、最終OUTPUTから逆算して設計するとよいと助言する)と、
  効果予測(`framework.md`「7. 効果予測の算出ロジック」の削減率目安を使い、Phase 5の月間ムダ時間から
  試算する)を埋める。
- `06_TOBEパターン設計.md` を埋める。

### Phase 7: 優先順位マトリクス

- Phase 6の各パターンについて、効果(0-10)と実行しやすさ(0-10)をユーザーと一緒にスコアリングする。
  評価が割れそうな場合は理由を聞き、`framework.md`の判断基準(承認の少なさ・システム連携要件・
  影響範囲・予算内で完結するか)に照らして一緒に整理する。
- `07_優先順位マトリクス.md` を埋め、着手順の推奨を書く。

### Phase 8: JSON化・レポート生成

1. `01`〜`07` の内容を、`harness/README.md`「JSONスキーマの要点」の形式に変換し、
   `harness/cases/<案件名>/data.json` として書き出す。
   - `asis.steps` は Phase 2の個別定義シート(Phase 3ですり合わせ済みの内容)から。
   - `issues` は Phase 5の課題一覧から。
   - `tobePatterns` は Phase 6のパターンごとに1要素、`effectLevel`/`ease` はPhase 7のスコアを転記。
2. 次のコマンドでレポートを生成する(JSONの構造チェックも兼ねる):
   ```
   node .claude/skills/business-analysis-guide/scripts/build_report.js \
     harness/cases/<案件名>/data.json \
     harness/cases/<案件名>/report.html \
     harness/report/template.html
   ```
   エラーが出た場合(存在しない担当者を参照している、必須キー漏れなど)はメッセージに従って
   `data.json` を修正し、再実行する。
3. 生成できたら `harness/cases/<案件名>/report.html` のパスをユーザーに伝える。ブラウザ操作の
   ツールが使える場合はスクリーンショットを撮って主要な問題(担当者の抜け、想定外のレーン分割など)
   がないか確認する。使えない場合は、PowerShellで既定ブラウザで開くことを提案する:
   ```
   Start-Process "harness/cases/<案件名>/report.html"
   ```
4. `PROGRESS.md` の全項目にチェックを入れる。

## 再開時の動き

このスキルが再度呼ばれたとき、まず `harness/cases/` を確認する。既存案件が1つならその
`PROGRESS.md` を読んで続きのフェーズから再開する。複数ある場合はどの案件を続けるかユーザーに聞く。
新規案件を始めたい旨が明言されている場合はPhase 0から始めてよい。

## 進め方の姿勢

- 1フェーズ = 1往復程度を目安にし、全フェーズを一気に質問攻めにしない。
- ユーザーが即答できない項目は「わからない/後で確認する」を許容し、`(要確認)` と書いて先に進める。
  分析全体を止めない。
- 各フェーズの終わりに、書き込んだ内容の要約を短く見せてから次のフェーズに進む。
